An agent skill

Give your coding agent a gut feeling.

The jevcli skill lets Claude Code, Codex or any agent hand small judgements to a decision model: is this urgent, which bucket, same customer, is this line an error. Each one comes back in about 0.4 s as a number or a key, so the agent saves its own reasoning for the real work.

What it looks like inside your agent (an example session)

You

Go through last night's app.log and fix whatever broke.

Agent, using the jevcli skill

jevcli ask --lines app.log --noul fail="Is this line a failure an on-call engineer would act on?" --parallel 8 \
  | jq -c 'select(.answers.fail.noul > .8)'

jevcli flagged 2 of 4,812 lines (P > 0.8): the payment gateway timeout at 02:14 and db connection refused at 02:15. Both come from the pool size change in db.go; the fix and a test are below.

The agent didn't read 4,812 lines. It asked one question in parallel, then worked on the two lines that mattered.

One command, your questions

Ask anything

A yes/no (--noul), pick one (--choice) or a rating (--score). Put as many as you like in one call.

Save them once

jevcli question add urgent …, then jevcli ask urgent,team from any agent, any repo.

Every knob is yours

Thresholds, parallelism, retries and timeouts come from config with sensible defaults, and can be set per profile or per question.

if jevcli is "Is this urgent?" < email.txt; then ...; fi   # yes 0.95
jevcli filter "Is this an error?" < app.log           # grep by meaning
jevcli rank "Is this about refunds?" --top 5 < results.txt

jevcli question add urgent --noul "Is this urgent for the person receiving it?" --yes 0.85
jevcli question add team --choice "Which team?|web=frontend;api=backend;billing=money"

echo "Checkout is down, customers are being charged twice" | jevcli ask urgent,team
urgent           yes        0.95
team             billing    0.87

jevcli ask --lines app.log --noul err="Is this an error?"      # JSONL, one verdict per line, in parallel

Exit codes are the contract: 0 yes, 1 no, 3 unsure, 4 error. An outage never reads as "no".

When the agent reaches for it

Triage a log, inbox or ticket queueask --lines with one yes/no, then act on the lines above 0.8
Sort items into bucketsask --states t.jsonl team (a saved choice)
Dedupe recordsask --noul same="Are A and B the same customer?"
Check a claim against a sourceask --noul ok="Does the text say payment is due in October?"
Rank search resultsask --lines results.txt --noul hit="Does this answer …?", then sort by p
About to ask you "A or B?"a --choice first; the agent asks only when the verdict is unsure
About to hand back a turnjudge: would you accept this, or did it stop short?

Built so the agent can trust it

Numbers, not prose

Every answer is a probability, a key or a level. The skill tells the agent to act only above 0.8 (or below 0.2) and to check anything in between.

Fast enough to fan out

20 tickets take 8.2 s one at a time and 1.5 s with --parallel 8.

Any Jev-like endpoint

Hosted Jev, a self-hosted model or your own. Keys stay in environment variables and are never written to disk.

Hooks off by default

An optional Claude Code Stop hook scores each turn. It stays off until you run jevcli hook enable stop.

Install

# macOS / Linux
curl -fsSL https://muthuishere.github.io/jevcli/install.sh | sh
# Windows
curl -fsSLo install.cmd https://muthuishere.github.io/jevcli/install.cmd && install.cmd

# point it at your endpoint (the key stays in your environment)
jevcli profile add jev https://your-endpoint/v1/systemone --model MODEL --header "Authorization: Bearer $YOUR_KEY_VAR"

This installs the skill in ~/.claude/skills and ~/.agents/skills (plus ~/.codex/skills if that folder exists), along with the small jevcli binary the skill calls. Read the skill itself: skill.md.

jevcli judges; it does not write. Your agent still writes the code and the reply, and now spends less effort on the small calls. Source on GitHub
