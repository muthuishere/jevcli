Ask

One command for every question: inline or saved, one input or a parallel batch, verdicts with probabilities, exit codes an agent can branch on.

The shortcuts#

Each is ask with one question already shaped; the same saved questions, context, settings and exit codes apply. is and pick print VERDICT P on one line. filter and rank read one input per line from stdin unless you pass --in, --lines or --states. pick needs at least two key=description options.

A saved yes/no question works as the question: jevcli is urgent < email.txt. filter and rank refuse a saved choice or score question, since they need P(yes).

The full command: ask#

Questions

  • Saved names: jevcli ask urgent,team < ticket.txt (see Saved questions).
  • Inline yes/no: --noul NAME="QUESTION". A second form spells out the poles: NAME="QUESTION|true means|false means".
  • Inline pick-one: --choice NAME="QUESTION|key=desc;key2=desc". The verdict is one key.
  • Inline rating: --score NAME="QUESTION|low;mid;high", lowest first. The verdict is one level.
  • A file: --questions set.json, a JSON object {NAME: {type, instructions, criteria}}.

Any number of questions go in one call and one request (up to chunk, default 32, per request). "noul" is the endpoint's name for a yes/no question, and the CLI keeps it.

Output lines are sorted by question name, not by the order you gave them.

Input

  • stdin (the default), or --in "text", --in @file, --in '{"json": "object"}', --in -.
  • --lines FILE (or -): a batch, one input per line of text.
  • --states FILE.jsonl (or -): a batch, one JSON object or string per line. A JSON input keeps its shape; context is merged into its "context" field.

Output for one input

One line per question: NAME VERDICT P. A yes/no verdict is yes, no or unsure (P at or above yes 0.8, at or below no 0.2, or between). A choice or score is the key or level, or unsure when its confidence is below min_confidence 0.6. --json prints the same as one JSON object; --raw prints the server's reply untouched.

Output for a batch

JSONL in input order, one object per input with line, input and answers. Each answer carries verdict and, for yes/no, p. Filter with jq.

Batches run parallel requests at a time (default 8; --parallel N for one call). A batch exits 0, or 4 if any input failed; that line carries an "error" field instead of answers.

Exit codes (one input)

codemeaningwhat an agent should do
0every question answered yes / decidedact

Overrides for one call

--yes, --no, --min, --parallel, --profile, --context TEXT|@file (repeatable), --no-context. Every command also takes --cwd DIR to run as if from that directory (it picks the folder's .jevcli/ and ## Jev section). Precedence: built-in < config < profile < the question's own thresholds < flags. See Settings.

judge: before handing a turn back#

judge asks four fixed questions about a proposed final message: would the user accept it, did the agent stop short, the likely reaction, and a 0-4 satisfaction. The questions come from a question pack (JSON); the built-in one is neutral, and a profile can point at its own with --questions pack.json.

The skill tells the agent: below accept_min 0.35 the user would likely push back, so verify and show evidence; above more_max 0.65 on "wanted more", finish the missing part. The call above scored 0.73 on wanted more for a one-line proposal with no diff shown, which is the intended nudge. judge is a heuristic from one model; the maintainers have not published an accuracy number for it, and neither do we.

Writing a question that works#

  • Say whose decision it is and what counts as yes: "Would a senior on-call engineer page someone for this line?" beats "bad?".
  • The model sees only the question, the input and the context; nothing from your conversation.
  • Put the facts that decide it in context, not in the question.
  • Look at a few verdicts before you loop over 5,000 lines. Tune thresholds per question if the default band is wrong for it.
