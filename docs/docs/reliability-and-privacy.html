Reliability & privacy

Exit codes an agent can trust, retries, a reply validator that fails closed, a ledger that stores no content, and a plain list of what leaves your machine.

Exit codes#

codewhen
0yes / decided (or a batch where every input succeeded)
1no
3unsure (in the band between no and yes, or a choice/score below min_confidence)
4any error: no profile, missing $VAR, network, HTTP error after retries, invalid reply, bad usage

The rule the code enforces: die exits 4, never 1. A dead endpoint cannot read as "no" in an if.

Retries#

HTTP 429, 5xx and network errors are retried with backoff, retries 3 times by default, timeout_s 60 per request. Other HTTP errors (401, 400) fail at once with the status and the first 300 characters of the body.

Fail-closed validation#

A reply is rejected, and the call is an error (exit 4), unless it answers exactly the questions asked with nothing extra, every probability is in [0, 1] and each distribution sums to 1 (±0.02), and a choice names one of the offered keys. A malformed or partial answer never becomes a verdict.

The ledger#

With ledger true (the default), every call appends one line to ~/.local/share/jevcli/calls.jsonl. It holds the host, model, number of questions, a 12-hex-character hash of the question set, latency, token usage and an error message if any. It never holds the input, the question text or a header. JEVCLI_LEDGER=off disables it for a shell.

That line is this machine, today, while writing these docs: 51 calls to the hosted endpoint, no errors, median 577 ms. Your numbers will differ with the endpoint and the network; the README's "about 0.4 s" is the maintainer's figure, and this is ours.

What leaves your machine#

sent to the endpointnever sent
the question text and optionsyour config file or profiles
the input (--in, stdin, each line of a batch)header values as text in the ledger
the merged ## Jev context and --context textanything from files you did not name
for judge: the request, the proposal, the --action linesfor plugins: the full transcript (the state is a short description of the event)
for plugins: a description of the event (the command, the fetched text, the prompt)

The endpoint is whatever the profile says. A hosted service sees the input and keeps whatever its terms say it keeps; a local model on 127.0.0.1 sees the same and keeps nothing you did not configure. The skill tells agents never to put secrets into --in or --proposal, and the maintainer's notes list "redaction before send" as not done yet, so treat that as your job today.

Keys#

A header like Authorization: Bearer $JEV_API_KEY is stored with the $VAR literal and expanded from the environment at request time. profile list prints the literal, not the value. If the variable is unset the call fails with its name (exit 4) rather than sending an empty header.

Hooks and plugins#

  • Installed disabled. hook status says what is in settings.json and whether anything ran.
  • Shadow mode scores in a detached process and cannot delay the agent.
  • act mode fails open: an endpoint error lets the tool call or the turn proceed.
  • stop-judge never blocks the same turn twice.
  • uninstall --hooks removes only jevcli's entries and backs up the settings file first.

Tests#

go test ./... covers reply validation, retries, the Stop gate, the section parser, context merging and plugin conditions against a fake server. There is no published accuracy benchmark for any question; the maintainer's notes record that a small personal model answered several cookbook recipes wrongly, which is the honest summary: the verdicts are only as good as the model behind the profile.
